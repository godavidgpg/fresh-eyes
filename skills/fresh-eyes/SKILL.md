# Fresh Eyes

목표는 "기능이 돈다"가 아니다. **처음 온 사람이 망설이지 않고 목적을 이루고, 화면이 믿을 만하고 의도적으로 디자인돼 보이는가**를 증명하는 것이다.

이 스킬이 다른 리뷰와 다른 점은 하나다. **에이전트는 사람보다 너무 많이 안다.** DOM, 접근성 트리, 컴포넌트 이름, 소스 코드를 읽으면 `aria-label="Export to CSV"`인 아이콘 버튼이 무엇인지 "그냥 알아버린다". 실제 사람은 그 아이콘을 보고 공유인지, 다운로드인지, 업로드인지 헷갈린다. 그래서 이 스킬은 **모든 판단을 두 번 한다.** 먼저 픽셀만 보고 사람처럼 추측하고, 그다음 구조와 실제 동작으로 정답을 확인한다. **두 판단이 어긋나는 지점이 곧 UX 결함이다.**

## 0. 핵심 원칙

1. **Blind-first: 픽셀 먼저, 이름은 나중.** 1~2단계를 기록하기 전에는 `browser_snapshot`, 소스 코드, `perceive.js` 결과를 보지 않는다. 판단은 `browser_take_screenshot` 이미지로만 한다. 이미 코드를 읽었다면 오염된 상태이니, 보고서에 그렇다고 적고 4-1의 "Fresh eyes 서브에이전트"를 쓴다.
2. **화면에 보이는 단서로만 행동한다.** 태스크를 수행할 때 누를 요소는 "화면 오른쪽 위의 파란 '저장' 버튼"처럼 **시각적 묘사로 먼저 고르고**, 그다음 snapshot의 ref에 대응시킨다. 접근성 이름을 보고 나서야 찾을 수 있었다면 그 자체가 지적 사항이다.
3. **모든 지적에는 근거가 있다.** 스크린샷 파일, 재현 단계, 측정값 중 하나 이상을 붙인다. 근거 없는 취향은 "취향" 섹션으로 따로 뺀다.
4. **관찰, 추정, 연구 근거를 구분한다.** "버튼이 28px이다"(관찰), "엄지로 누르기 어렵다"(추정), "WCAG 2.5.8 최소 24px"(기준).
5. **사용성이 먼저, 미감은 그다음이다.** 예쁜 UI는 더 쓰기 쉽다고 느껴진다(심미적 사용성 효과, Kurosu & Kashimura 1995). 그래서 미감이 사용성 문제를 가린다. 대비, 크기, 라벨을 희생하는 디자인 수정안은 내지 않는다.
6. **사람의 목소리로 쓴다.** 지적마다 실제 앱 리뷰에 달릴 법한 한 문장을 붙인다. 쓰는 법은 [references/voice-of-user.md](references/voice-of-user.md)에 있다.
7. **많이가 아니라 중요한 것.** 최종 지적은 15개까지, 심각도 순으로.
8. **부작용이 있는 동작은 묻는다.** 결제, 발송, 삭제, 실제 계정 변경 전에는 사용자에게 확인한다. 테스트 계정과 테스트 데이터를 쓴다.

## 1. 준비

이미 받은 정보가 아니면 묻는다(질문 도구가 있으면 그것으로).
- **대상**: URL(로컬 dev 서버 가능), 로그인 필요 여부와 테스트 계정, 코드 접근 가능 여부
- **페르소나**: 누가 쓰는가. 고를 수 있는 기본 세트는 [references/personas.md](references/personas.md)
- **핵심 태스크 1~3개**: 꼭 해내야 하는 일 (예: "가입하고 첫 송금하기")
- **모드**: Quick(화면 1~2개, 1·2·5·8단계, 15분) 또는 Full(전 단계)

답이 없으면 기본값을 쓰고 보고서 맨 위에 적는다. 페르소나는 "처음 온 일반 사용자, 모바일 한 손", 태스크는 "첫 화면의 주요 행동을 끝까지 따라가기", 모드는 Full.

**도구.** Playwright MCP(`claude mcp add playwright npx @playwright/mcp@latest`)를 쓴다.
- 보기: `browser_navigate`, `browser_resize`, `browser_take_screenshot`(`fullPage`), `browser_snapshot`
- 행동: `browser_click`, `browser_type`, `browser_fill_form`, `browser_hover`, `browser_press_key`, `browser_select_option`, `browser_wait_for`, `browser_navigate_back`
- 진단: `browser_evaluate`, `browser_console_messages`, `browser_network_requests`, `browser_emulate_media`(다크 모드, reduced-motion)
- 좌표로 누를 때(`--caps=vision`): `browser_mouse_click_xy`. 사람은 좌표를 누르므로, ref가 아니라 **보이는 위치를 누르는 테스트**에 유용하다.

MCP가 없으면 [scripts/capture.mjs](scripts/capture.mjs)로 스크린샷과 측정값을 한 번에 뽑는다(`node <스킬 폴더>/scripts/capture.mjs <url> qa`, 프로젝트에 `playwright` 필요). 이때도 PNG를 먼저 보고 `measurements.json`은 나중에 연다.

**측정 스크립트 쓰는 법.** `scripts/perceive.js`와 `scripts/tokens.js`는 `() => { ... }` 함수 하나로 되어 있다. 파일 내용 전체를 Read로 읽어서 `browser_evaluate`의 `function` 인자에 그대로 넣는다. Claude in Chrome 같은 다른 브라우저 도구도 같은 절차로 쓸 수 있다.

**뷰포트.** 모바일 390×844, 데스크톱 1440×900을 기본으로 본다. 스크린샷은 `qa/<화면>-<뷰포트>-<상태>.png`로 이름 붙인다.

## 2. 1단계: 첫 눈 (50ms → 5초)

사람은 50ms 안에 화면이 마음에 드는지 판단하고, 그 판단은 오래 바뀌지 않는다(Lindgaard et al. 2006). 시각적 복잡도가 낮고 장르의 전형을 따르는 화면이 더 좋게 평가된다(Tuch et al. 2012). 그래서 첫 화면부터 따로 본다.

각 뷰포트에서 스크롤하지 않은 첫 화면을 찍고, **이미지만 보고** 아래를 기록한다.
1. **첫인상 형용사 3개** (예: "빽빽함, 믿음직함, 템플릿 같음")
2. **이건 무슨 서비스인가?** 한 문장으로 말할 수 있는가
3. **예상 시선 순서 ① → ⑤**: 무엇이 먼저 보이는가. 예측 규칙은 [references/perception.md](references/perception.md)에 있다 (크기, 대비, 고립, 얼굴과 큰 숫자, 왼쪽 위 편향)
4. **가장 먼저 누를 곳**과 그 이유
5. **눈 찡그리기 테스트**: 흐린 화면을 찍는다. 덩어리가 몇 개로 보이는가? 가장 진한 덩어리가 핵심 행동인가?
   ```js
   () => { document.documentElement.style.filter = 'blur(6px)'; return 'squint on' }
   ```
6. **흑백 테스트**: 색을 빼도 상태(오류, 선택, 비활성)를 구분할 수 있는가?
   ```js
   () => { document.documentElement.style.filter = 'grayscale(1)'; return 'gray on' }
   ```
   끝나면 `() => { document.documentElement.style.filter = ''; return 'reset' }`로 되돌린다.

기록한 **뒤에** `browser_evaluate`로 [scripts/perceive.js](scripts/perceive.js)를 실행한다. 이 스크립트는 크기, 대비, 채도, 위치로 시각적 무게를 계산해 **휴리스틱 시선 순서**를 낸다. 내 예측, 스크립트 순서, **제작자가 의도한 우선순위**(가장 중요한 행동) 세 가지를 비교한다. 핵심 행동이 5위 안에 없으면 지적한다. 스크립트 순서는 아이트래킹 모델이 아니라 근사치이니, 보조 근거로만 쓴다.

## 3. 2단계: 이름 모르는 사람 테스트 (Blind Control Reading)

사용자 요청의 핵심이다. 사람은 버튼의 호출명을 모르고, **보이는 모양과 글자에서 기능을 추측한다.** 절차는 [references/comprehension.md](references/comprehension.md)에 자세히 있다.

1. 첫 화면 스크린샷에서 눌릴 것 같은 요소와 헷갈리는 요소를 **모두** 번호 매겨 적는다. 각각에 대해:
   - **보이는 모습**: "오른쪽 위, 화살표가 박스 밖으로 나가는 아이콘, 라벨 없음"
   - **추측한 기능**: 사용자의 말로 ("공유하기?")
   - **확신도**: 높음 / 중간 / 낮음
   - **누를 용기**: 누르면 되돌릴 수 있을 것 같은가, 무서운가
   - **눌릴 것처럼 보이는가**: 예 / 애매 / 아니오
2. 그다음 `perceive.js`의 `controls`(보이는 글자 vs 접근성 이름, 아이콘 전용 여부, 시그니파이어 강도)와 `browser_snapshot`을 읽는다.
3. 확신도가 낮거나 중간이던 요소 중 부작용 없는 것 몇 개를 **실제로 눌러서** 결과를 확인한다.
4. 어긋남을 다섯 유형으로 분류한다(Gaver 1991의 affordance 분류 확장).

| 유형 | 의미 | 예 |
|---|---|---|
| **의미 불일치** | 추측한 기능과 실제 기능이 다름 | 다운로드인 줄 알았는데 공유 시트가 열림 |
| **숨은 어포던스** | 눌리는데 눌릴 것처럼 안 보임 | 회색 일반 텍스트처럼 생긴 링크, 카드 전체가 링크인데 단서 없음 |
| **거짓 어포던스** | 눌릴 것처럼 보이는데 안 눌림 | 파란 밑줄 텍스트, 버튼처럼 생긴 배지 |
| **이름 불일치** | 보이는 글자와 접근성 이름이 다름 (WCAG 2.5.3) | 화면엔 "시작", 이름은 `submit-btn-primary` |
| **정보 냄새 부족** | 라벨만 봐서는 누르면 어디로 가는지 모름 | "더보기", "바로가기", "클릭" |

**Fresh eyes 서브에이전트 (권장).** Agent 도구가 있으면 코드나 DOM 맥락 없이 **스크린샷 파일 경로와 페르소나만** 넘겨 1~2단계를 따로 시킨다. 이미 앱을 아는 내 판단보다 훨씬 사람에 가깝다. 프롬프트 틀은 [references/comprehension.md](references/comprehension.md)의 마지막 절에 있다. 내 판단과 서브에이전트 판단이 갈리면 둘 다 보고서에 적는다.

## 4. 3단계: 태스크 수행 (보이는 것만으로)

핵심 태스크를 실제로 끝까지 해본다. 원칙 2를 지킨다. **매 단계마다 스크린샷만 보고 다음 행동을 고르고**, 고른 이유를 시각적 단서로 적은 다음 ref에 대응시켜 실행한다.

각 단계에서 인지적 워크스루(Wharton et al. 1994)의 네 질문에 답한다.
1. 사람이 지금 **이걸 하려고** 할까? (목표와 화면이 맞물리는가)
2. 해야 할 행동이 **눈에 띄는가?** (발견 가능성)
3. 그 행동이 원하는 결과로 이어진다고 **연결 지을 수 있는가?** (라벨, 아이콘, 정보 냄새)
4. 행동한 뒤 **진행됐다는 걸 알 수 있는가?** (피드백이 시선이 있던 자리에 나타나는가)

하나라도 "아니오"면 **망설임 지점**이다. Norman의 두 간극으로 나눠 적는다. **실행의 간극**은 어떻게 하는지 모르는 것이고, **평가의 간극**은 결과가 어떻게 됐는지 모르는 것이다.

함께 센다.
- 클릭 수, 화면 전환 수, 되돌아간 횟수, 잘못 누른 횟수
- **탐색 비용**: 다음 행동을 찾을 때 화면에서 훑어본 후보 수(내가 고민한 요소 수)
- **응답 시간**: 0.1초 즉각, 1초 넘으면 흐름이 끊김, 10초 넘으면 이탈 (Nielsen 1993). 400ms 넘는 동작에 진행 표시가 없으면 지적한다
- **피드백 위치**: 결과가 시선 밖(화면 구석 토스트)에만 나타나면 놓치기 쉽다 (변화맹, Rensink et al. 1997)

상호작용 법칙(Fitts, Hick, 인지 부하, 폼, 다크 패턴)의 체크 항목은 [references/interaction.md](references/interaction.md)에 있다.

## 5. 4단계: 상태 스트레스 테스트

AI가 만든 앱이 가장 자주 빠뜨리는 부분이다. 해당하는 것만 하고, 목록 전체는 [references/interaction.md](references/interaction.md)에 있다.
- **빈 상태, 로딩, 에러**: 다음 할 일을 알려주는가. 이유 없이 회색으로 비활성화된 버튼은 없는가
- **새로고침, 뒤로 가기**: 입력, 필터, 단계가 살아남는가
- **연타**: 제출 버튼을 두 번 누르면 중복 처리되는가
- **극단적 콘텐츠**: 긴 한국어 이름, 999,999, 이모지, 빈 값
- **키보드만으로**: Tab 순서, 보이는 포커스, Enter와 Esc
- **200% 확대, 320px 폭**: 가로 스크롤, 화면을 가리는 고정 헤더
- **다크 모드, 동작 줄이기**: `browser_emulate_media`
- **콘솔과 네트워크**: 사람 눈에 안 보이는 실패 원인

## 6. 5단계: 디자인 감각 평가 (unslop 렌즈)

사용성 다음에 **의도적으로 디자인돼 보이는가**를 본다. 이 렌즈는 unslop(Damir Sokolovsky, CC BY 4.0)의 진단 체계를 평가용으로 옮긴 것이다. unslop은 화면을 고치는 도구이고, 이 단계는 **고치지 않고 판정한다.**

1. 1440과 390 fullPage 스크린샷으로 먼저 눈으로 판단한다.
2. [scripts/tokens.js](scripts/tokens.js)를 실행해 글자 크기, 색, 간격, 모서리 종류와 "AI 티" 신호(그라데이션 텍스트, 컬러 글로우, 이모지 아이콘, 대문자 자간 라벨, 무한 반복 애니메이션, `transition: all`, 느낌표)를 센다.
3. [references/visual-craft.md](references/visual-craft.md)의 **9개 차원 루브릭**으로 1~5점을 매기고, 점수마다 스크린샷 근거를 한 줄씩 붙인다.
4. **템플릿 테스트**: 제품 이름을 다른 제품으로 바꿔도 화면이 그대로 어울리는가? 그렇다면 정체성 점수를 깎는다.
5. 수정안은 토큰 단위로 쓴다 ("글자 크기 11종을 12/14/16/20/28/40으로").

## 7. 6단계: 페르소나와 접근성 패스

1단계에서 고른 페르소나의 **행동 파라미터**(어휘 수준, 아이콘 이해도, 한 손 사용, 시력, 인내심)를 적용해 핵심 화면을 한 번 더 본다. 페르소나별 체크 항목과 시뮬레이션 방법(확대, 흑백, 엄지 영역, 키보드)은 [references/personas.md](references/personas.md)에 있다. WCAG 2.2 AA의 핵심 항목(대비 1.4.3, 리플로 1.4.10, 포커스 표시 2.4.7, 포커스가 가려지지 않음 2.4.11, 이름 안의 라벨 2.5.3, 타깃 크기 2.5.8)은 측정값으로 확인한다.

## 8. 7단계 (선택): 레퍼런스 비교와 실제 리뷰로 보정

- **레퍼런스 앱**: 같은 유형의 패턴에서 잘 만든 앱(예: 송금은 Toss, 결제 폼은 Stripe, 키보드 흐름은 Linear)을 [references/reference-apps.md](references/reference-apps.md)에서 골라 **무엇이 다르게 느껴지는지** 말로 짚는다. 베끼라는 뜻이 아니라 비교 기준을 세우려는 것이다. 가능하면 같은 뷰포트로 공개 페이지를 찍어 나란히 둔다.
- **실제 리뷰**: 경쟁 서비스나 비슷한 앱의 스토어 리뷰와 커뮤니티 글에서 반복되는 불만 3~5개를 WebSearch로 모은다. Khalid et al.(2015)의 12가지 불만 유형에 대응시키고, 같은 불만이 이 서비스에도 해당하는지 확인한다. 방법은 [references/voice-of-user.md](references/voice-of-user.md)에 있다.

## 9. 8단계: 판정과 보고서

심각도(Nielsen 0~4), 점수표, 출시 판정, 보고서 템플릿은 [references/scoring-report.md](references/scoring-report.md)에 있다. 요약하면 다음과 같다.
- **한 줄 진단**: 처음 온 사람이 겪는 핵심 문제
- **첫 눈 결과**: 예측 시선 순서와 의도의 차이
- **이름 모르는 사람 테스트 표**: 요소마다 추측, 실제, 유형
- **태스크 결과**: 성공 여부, 클릭 수, 망설임 지점, 간극 유형
- **지적 최대 15개**: 위치, 사용자 목소리, 관찰, 원칙, 수정안, 증거
- **점수**: 사용성 지수(UX) + 디자인 감각(Craft) + 판정 (출시 / 고치고 출시 / 보류)
- **잘된 점**: 고치다가 망가뜨리지 않도록 유지할 것
- **한계**: 오염 여부, 확인 못 한 상태, 추정에 의존한 부분

사용자가 수정했다면 같은 뷰포트와 같은 태스크로 다시 돌리고, 지적마다 해결됨 / 부분 해결 / 미해결을 표시한다. 전후 스크린샷을 나란히 둔다.

## 하지 말 것

- 접근성 트리나 코드를 먼저 읽고 "사람도 알 것"이라고 가정하지 않는다
- 측정 스크립트 결과만으로 지적하지 않는다. 화면에서 실제로 거슬리는지 확인한다 (이미지 위 텍스트는 대비가 틀리게 나올 수 있다)
- 휴리스틱 시선 순서를 "아이트래킹 결과"라고 쓰지 않는다
- 연구 수치를 지어내지 않는다. 근거는 [references/sources.md](references/sources.md)에 있는 것만 인용하고, 모르면 원칙 이름만 쓴다
- 사용자 확인 없이 결제, 발송, 삭제를 실행하지 않는다
- 좋은 화면을 억지로 깎아내리지 않는다. 문제가 적으면 적다고 말하고 잘된 점을 구체적으로 적는다
